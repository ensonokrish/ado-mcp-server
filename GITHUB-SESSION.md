# GitHub session ticketing server

This is a separate stdio MCP server, independent of the ADO server and keytar at runtime. It uses `gh api` on `github.com`, with the existing GitHub CLI login. Install Node.js 18+ and GitHub CLI, authenticate `gh` beforehand, and ensure the authenticated account has access to the configured repositories and Projects. Projects v2 reads and writes require the account's appropriate project access and CLI token scopes (typically `read:project` for reads and `project` for writes). SSO organizations may require authorization. This server never starts authentication, changes accounts, or reads or prints the token. Unset both `GH_TOKEN` and `GITHUB_TOKEN` before starting it; either variable causes requests to fail. The server verifies the active github.com account with `gh auth status --json hosts` (without `--show-token`) and requires successful authentication with `tokenSource: keyring`; plaintext or unknown storage is refused. A gh version supporting JSON auth status is required.

Set these environment variables in the MCP client before starting the server:

* `SRE_BUDDY_GITHUB_ALLOWED_REPOSITORIES`: JSON array of `owner/repo` strings, for example `["example/service"]`. Repository actions require a nonempty allowlist and an exact match.
* `SRE_BUDDY_GITHUB_ALLOWED_PROJECTS`: JSON array of `owner/project-number` strings, for example `["example/12"]`. Project actions require an exact match; moves require both projects. Owners must appear in at least one allowlist.

Compile without setup side effects with `npx tsc` (or `npm run test:github` for focused tests), then run `npm run start:github` or `node dist/github-index.js`. Unlike `npm run build`, these do not run the existing postbuild setup script. The test command runs the original PAT client tests as well.

## Tool contract

`github_work` accepts a flat object with `action` and these optional parameters: `owner`, `repo`, `issue_number`, `project_number`, `source_project_number`, `title`, `body`, `labels`, `assignees`, `state` (`open` or `closed`), `state_reason` (`completed`, `not_planned`, or `reopened`), `milestone_number` (positive integer or null), `issue_type`, `parent_issue_number`, `related_url`, `field_name`, `field_value` (string, number, or null), `query`, `limit` (1–100), and `request_key` (1–128 ASCII letters/digits/`_.:-`, starting with a letter or digit). Numbers must be positive safe integers. `owner` is required except for `session`.

* `session`: `data.user` has `login` and `name`.
* `list_projects`, `get_project`, `list_project_items`: owner and, except for listing, project number. Item listing optionally takes repo and issue number together for exact membership lookup. Results expose issue number, full repository name, and URL and omit items whose repository is not allowlisted. Drafts are omitted.
* `list_issues`, `search_issues`, `get_issue`, `list_comments`, `list_assignees`, `list_labels`, `list_milestones`: owner and repo; issue and comments reads require issue number. Issue-type listing uses `list_issue_types` and requires only owner.
* `create_issue`: owner, repo and title; optional body, labels, assignees, milestone, issue type, and request key. It creates only the issue, not a Project item. For a request key, an exact visible `SRE-Buddy reference: <key>` line is added if not already present, and existing matches are searched first. A matching issue is returned with `recovered: true`. GitHub search is eventually consistent and concurrent requests are not atomic; callers must journal uncertain creates and explicitly search/reconcile, not automatically retry creation.
* `update_issue`: owner, repo, issue number and at least one issue field. Labels and assignees replace the entire list; `[]` clears. `milestone_number: null` clears the milestone. Both create and update validate supplied labels, assignees, milestone and type, and verify returned fields.
* `add_comment`: issue and body. `link_issue` and `link_pr`: issue and an allowlisted `https://github.com/owner/repo/issues/N` or `/pull/N` URL; these add an explicit comment, not native closing linkage.
* `add_to_project`, `remove_from_project`, `move_project`: issue and destination project; move additionally requires source project. Add is idempotent. Move adds and verifies the destination before attempting source removal. Error data includes progress; `source_removed: null` means the removal outcome needs reconciliation.
* `set_project_field`: issue, project, field name and value. Supports live single-select option names, iteration titles or `@current`, text, number, date (`YYYY-MM-DD`), and null to clear; reads the field back. `@current` uses UTC dates and requires one matching iteration.
* `validate_project_field`: read-only validation of the same field name and value using the same live schema, without requiring an issue; returns `data.valid: true`.
* `set_parent`, `remove_parent`: issue; setting also requires a different parent issue number in the same repository. These use native sub-issues and verify the resulting parent.

Every successful tool response has JSON text `{ "ok": true, "data": ... }`. Lists use `data.items`; issue results use `data.issue` with `number`, `url`, `title`, `state`, `body`, `type` (object with `name` or null), and GitHub fields. Errors use `{ "ok": false, "error": "...", "data"?: ... }` and MCP `isError: true`; when an issue write completed but readback failed, `data.issue` contains the write response. Create errors include `data.mutation_attempted: false` only before dispatch; true means the result may be uncertain. No request or response bodies are logged.

Requests are bounded to 30 seconds and 2 MiB of subprocess output. Lists return at most `limit` items (default 50, maximum 100); project item listings expose `has_more`, and search results expose `total_count` and `incomplete_results`. There is no general pagination cursor. A project with over 100 fields, or an issue with over 100 memberships when the requested project was not found, fails rather than guessing. Search accepts plain text or the exact scoped recovery query `repo:owner/repo is:issue "SRE-Buddy reference: key" in:body`; other qualifiers are rejected. Label preflight inspects the first 100 labels and therefore can reject valid labels beyond that bound.
